# Базовые правила Product Delivery

Эти правила применяются ко всем продуктам и фичам в проекте.

## Общие принципы

1. **Всегда начинай с плана и перечисления ожидаемых артефактов.**
   - Не начинай работу без плана
   - Чётко определи, какие артефакты будут созданы
   - Укажи формат каждого артефакта (таблица, список, диаграмма, PRD/Spec/Checklist)

2. **Всегда фиксируй допущения как "ASSUMPTIONS".**
   - Не угадывай контекст
   - Явно указывай все допущения
   - Записывай их в отдельный раздел "ASSUMPTIONS"

3. **Всегда давай критерии готовности (DoR/DoD).**
   - Definition of Ready (DoR) — что должно быть готово перед началом
   - Definition of Done (DoD) — что должно быть готово для завершения
   - Чёткие acceptance criteria для каждой задачи

4. **Всегда указывай метрики успеха и события аналитики для фич.**
   - North Star Metric
   - Supporting metrics
   - Guardrail metrics
   - События аналитики (event taxonomy)

## Формат артефактов

Предпочтительные форматы:
- **Списки** — для перечислений, чек-листов
- **Таблицы** — для структурированных данных, сравнений
- **Диаграммы в тексте** — для процессов, архитектуры (mermaid, ASCII)
- **PRD/Spec/Checklist** — для требований и спецификаций

Избегай:
- Длинных рассуждений без конкретных выводов
- Неструктурированного текста
- "Разговора" вместо артефактов

## Чек-лист качества

Каждый артефакт должен содержать:

- ✅ Явные допущения (ASSUMPTIONS)
- ✅ Границы (IN/OUT scope)
- ✅ Артефактный результат (таблица/список/спека), не рассуждения
- ✅ Acceptance criteria и edge cases (для требований)
- ✅ Метрики и события (для фич)
- ✅ Риски и mitigation (для delivery/tech/legal)

## Связь с документацией

Все артефакты должны быть связаны с:
- `docs/core/REQUIREMENTS.md` — требования
- `docs/core/UX_MAP.md` — карта опыта пользователя
- `docs/core/TESTS.md` — тесты и acceptance criteria
- `docs/core/WORKPLAN.yaml` — план работы
